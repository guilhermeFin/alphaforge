Quickstart

AlphaForge is a research engine, not a chart toy. You hand it a price series and a signal, and it hands back an equity curve plus a verdict on whether the result is likely to survive contact with a live market. Everything runs from plain Python — there is no hidden state and no opaque scoring.

The core loop is one call: feed backtest() a close price series and a signal (your target position or weight per bar), and inspect the returned BacktestResult. The summary() method already folds in transaction costs and reports the statistics that matter under multiple testing.

# a complete honest backtest in five lines
from research.backtest import backtest

res = backtest(close, signal, cost_bps=5.0, execution_lag=1)
print(res.summary(n_trials=20))   # Sharpe, deflated/probabilistic Sharpe, CVaR
equity = res.equity                # cost-adjusted equity curve

The n_trials argument is the part most backtesters quietly skip. It tells the engine how many strategy variants you tried before settling on this one, so the reported Sharpe can be deflated for selection bias. Pass an honest number — that is the whole point.

A backtest that does not know how many configurations you searched cannot tell you whether the result is real. AlphaForge makes n_trials a first-class input precisely so it can refuse to flatter you.

Installation

The research engine is a Python package with a small dependency footprint — NumPy and pandas for the maths, FastAPI and Uvicorn for the optional service layer. Clone the repository, create a virtual environment, and install in editable mode while you work against it.

# clone and install the research engine
git clone https://github.com/alphaforge/alphaforge.git
cd alphaforge
python -m venv .venv && source .venv/bin/activate
pip install -e "."

# run the verification suite — 178 tests, all green before you build on it
pytest -q

Run the test suite before you trust a single number. AlphaForge ships its honesty guarantees as executable tests, not as marketing copy, so a clean pytest run is your proof that the engine behaves as documented on your machine.

Backtest

The backtest() function in research/backtest.py is the entry point for the whole engine. It applies execution lag so a signal observed on bar t trades on bar t+1, charges costs on every change in position, and compounds the result into an equity curve. No look-ahead, no costless rebalancing.

Costs are expressed in basis points per unit of turnover via cost_bps, and periods_per_year controls annualisation — 252 for daily bars, 52 for weekly, and so on. The defaults below are deliberately conservative.

from research.backtest import backtest

res = backtest(
    close,
    signal,
    cost_bps=5.0,            # round-trip cost per unit turnover
    execution_lag=1,         # trade on the bar after the signal
    periods_per_year=252,    # daily annualisation
)

# BacktestResult exposes the curve, the returns, and the verdict
res.equity        # cost-adjusted equity series
res.returns       # per-bar net returns
res.summary(n_trials=20)   # dict of headline statistics

The returned BacktestResult carries .equity and .returns for plotting or further analysis, while .summary(n_trials) rolls everything into the statistics described in the Metrics section.

Metrics

Performance statistics live in research/metrics.py. The high-level summarize() function produces the same dictionary that BacktestResult.summary() returns, but you can also call each statistic directly when you want to reason about one number at a time.

Three of these are the difference between a real edge and a curve-fit. annualised_sharpe() is the familiar headline. probabilistic_sharpe_ratio() asks whether the observed Sharpe is reliably above zero given the sample length and the higher moments of the return distribution. deflated_sharpe_ratio() goes further and discounts for the number of trials you ran.

from research.metrics import (
    summarize, annualised_sharpe,
    probabilistic_sharpe_ratio, deflated_sharpe_ratio,
    conditional_var,
)

stats = summarize(res.returns, n_trials=20)
sr    = annualised_sharpe(res.returns)
psr   = probabilistic_sharpe_ratio(res.returns)
dsr   = deflated_sharpe_ratio(res.returns, n_trials=20)
cvar  = conditional_var(res.returns)   # historical tail loss (CVaR)

The conditional_var() function reports historical CVaR — the average loss in the worst slice of the return distribution — so you size risk against the tail you actually saw, not a tidy normal approximation that pretends the tail is thin.

Walk-forward

A single in-sample backtest is a hypothesis, not evidence. research/walkforward.py provides walk_forward(), which slices the history into sequential folds and evaluates each out-of-sample segment using only information available before it. The aggregate is far harder to overfit than one full-sample run.

The purge_bars and embargo_bars arguments are what make the split honest. Purging drops training observations whose labels overlap the test window; embargo holds out a buffer immediately after each test fold so leakage from autocorrelation cannot bleed across the boundary.

from research.walkforward import walk_forward, split_backtest

wf = walk_forward(
    close,
    signal,
    n_splits=5,
    cost_bps=5.0,
    purge_bars=5,        # drop overlapping training labels
    embargo_bars=10,     # buffer after each test fold
)

# split_backtest() runs a single in/out-of-sample partition
single = split_backtest(close, signal, cost_bps=5.0)

Use split_backtest() when you want a single clean train/test partition rather than the full rolling sequence — for example, to sanity-check a candidate before committing it to a longer walk-forward run.

Deflated Sharpe

The deflated Sharpe ratio is AlphaForge's central honesty guard. When you test many configurations and keep the best, the maximum Sharpe you observe is inflated by chance alone. deflated_sharpe_ratio() corrects for this by asking how impressive your best result is relative to the distribution of best results you would expect from noise after that many trials.

The mechanism is simple to use and hard to fool: the more variants you searched, the higher the bar your Sharpe must clear to register as significant. Feed it the net returns and the honest trial count.

from research.metrics import deflated_sharpe_ratio

# the same strategy, judged against how hard you searched
dsr_few  = deflated_sharpe_ratio(res.returns, n_trials=5)
dsr_many = deflated_sharpe_ratio(res.returns, n_trials=500)

# dsr_many is lower: 500 trials means a high Sharpe is cheaper to find by luck

A deflated Sharpe near or below zero is the engine telling you the result is indistinguishable from a lucky draw. That is a feature. The probabilistic Sharpe ratio is its companion for the single-trial case, accounting for sample length and the skew and kurtosis of returns.

PBO / CSCV

Where the deflated Sharpe judges a single chosen strategy, the Probability of Backtest Overfitting (PBO) judges your selection process. research/overfitting.py implements PBO via Combinatorially Symmetric Cross-Validation (CSCV): it repeatedly splits your trials into in-sample and out-of-sample halves and measures how often the in-sample winner underperforms out of sample.

Pass a returns matrix — one column per strategy variant, one row per bar — to cscv_pbo(). A PBO above 0.5 means your best in-sample strategy is more likely than not to be a below-median performer out of sample, which is a blunt signal that your search has overfit the data.

from research.overfitting import cscv_pbo, compact_pbo, pbo_from_factor_grid

# returns_matrix: shape (n_bars, n_variants)
pbo = cscv_pbo(returns_matrix, n_splits=8)
print(pbo)   # > 0.5 means the selection is probably overfit

# convenience wrappers for common shapes
quick = compact_pbo(returns_matrix)
grid  = pbo_from_factor_grid(close, signal_grid)

Use pbo_from_factor_grid() when your variants come from sweeping factor parameters — it builds the returns matrix from the grid for you and reports the PBO of the whole sweep, not just the winner you happened to like.

Trial ledger

Honest deflation requires an honest trial count, and most overfitting happens quietly across sessions rather than in one obvious sweep. The TrialLedger in research/trial_ledger.py records every configuration you evaluate so that n_trials reflects your real search history instead of the one run you remember.

The ledger reports an effective_n_trials floor — correlated variants count for less than a full independent trial, but the count never drops below a conservative minimum. You can never accidentally tell the engine you searched less than you did.

from research.trial_ledger import TrialLedger

ledger = TrialLedger()
ledger.record("momentum_20", res_a.returns)
ledger.record("momentum_40", res_b.returns)
ledger.record("meanrev_5",   res_c.returns)

n = ledger.effective_n_trials()      # floored, correlation-aware
dsr = deflated_sharpe_ratio(best.returns, n_trials=n)

Wire the ledger's effective_n_trials() straight into deflated_sharpe_ratio() and your significance test automatically accounts for the full breadth of your search.

Signal quality

Before a signal earns a backtest, it should earn a scorecard. research/signal_quality.py provides scorecard(), which evaluates a raw signal against forward returns and reports its predictive structure — information coefficient, sign stability, and decay — independent of any position-sizing or cost assumptions.

This separates two questions that backtests usually tangle together: does the signal contain information, and does your implementation extract it. A strong scorecard with a weak backtest points at execution; a weak scorecard means there was nothing to extract in the first place.

from research.signal_quality import (
    scorecard, compact_scorecard, ic_sign_stability,
)

card = scorecard(signal, close)        # full diagnostic report
quick = compact_scorecard(signal, close)
stability = ic_sign_stability(signal, close)   # does IC keep its sign?

The ic_sign_stability() check is especially telling: an information coefficient that flips sign across sub-periods is usually noise wearing the costume of an edge.

Data providers

Fundamental data is only useful if it is point-in-time, and survivorship or restatement bias is one of the quietest ways to manufacture a fake edge. research/providers.py exposes get_fundamental_provider(), a single factory that returns a provider conforming to one interface regardless of source.

The "synthetic" provider generates clean, reproducible data for tests and tutorials. The "simfin" and "sharadar" providers connect to real point-in-time datasets so your fundamentals reflect what was actually knowable on each date.

from research.providers import get_fundamental_provider

# swap sources without touching downstream code
provider = get_fundamental_provider("synthetic")   # or "simfin" / "sharadar"
obs = provider.fetch(symbols, fields)

# point-in-time by construction — no look-ahead from restatements

Because all three providers share an interface, you can prototype against synthetic data and switch to a paid point-in-time source by changing one string — the rest of your research code never knows the difference.

Factor library

Common cross-sectional factors are implemented once, correctly, in research/factor_lib.py — including gross_profitability, roe, and a set of value and quality constructions. They consume the standardised fundamentals built by build_fundamentals() in research/fundamentals.py.

The workflow is deliberately linear: fetch point-in-time observations from a provider, assemble them into an aligned fundamentals panel, then compute factors over that panel. Each step is independently testable.

from research.fundamentals import build_fundamentals
from research.factor_lib import gross_profitability, roe

fund = build_fundamentals(obs, index, symbols)

gp  = gross_profitability(fund)   # quality factor
qroe = roe(fund)                  # return on equity

# feed a factor straight into a signal, then backtest it honestly
signal = gp.rank(axis=1)

Building factors from a point-in-time panel keeps the look-ahead discipline of the data layer intact all the way through to your signal, so the honesty you bought at the provider is not quietly thrown away three lines later.

API

The engine ships an optional FastAPI service for teams that prefer to call the backtester over HTTP. It exposes a small, stable surface: GET /health for liveness, GET / for service metadata, POST /backtest to run an evaluation, and POST /session/reset to clear server-side state between runs.

Interactive, auto-generated documentation is served at /docs, so you can explore request and response schemas in the browser without leaving the running service.

# start the service
uvicorn api.main:app --reload

# run a backtest over HTTP
curl -X POST http://localhost:8000/backtest \
  -H "Content-Type: application/json" \
  -d '{"close": [100, 101, 99, 102], "signal": [0, 1, 1, 0], "cost_bps": 5.0, "n_trials": 20}'

# clear server-side session state
curl -X POST http://localhost:8000/session/reset

# liveness check
curl http://localhost:8000/health

The response from POST /backtest mirrors BacktestResult.summary() — the same deflated and probabilistic Sharpe, CVaR, and headline statistics you get from the Python API. The HTTP layer is a thin wrapper, not a separate implementation.

Methodology

AlphaForge exists to make it hard to lie to yourself. Every design choice in the engine is in service of one promise: a number it reports is a number that has already survived the standard ways backtests deceive their authors. The guarantees below are not aspirational — each is enforced and verified.

  • Point-in-time data. Fundamentals flow through get_fundamental_provider() and build_fundamentals() so factors only ever see what was knowable on each date — no restatement or survivorship leakage.
  • Costs and execution lag. backtest() charges cost_bps on every change in position and applies execution_lag so signals trade on the following bar. There is no free rebalancing and no look-ahead fill.
  • Deflated and probabilistic Sharpe. deflated_sharpe_ratio() discounts for the number of trials searched; probabilistic_sharpe_ratio() accounts for sample length and return higher moments. A high raw Sharpe is not enough.
  • Probability of Backtest Overfitting. cscv_pbo() measures how often your in-sample winner fails out of sample, judging the selection process rather than the survivor.
  • Honest trial counting. TrialLedger tracks your real search history and reports a correlation-aware effective_n_trials floor that feeds the deflation directly.
  • Purge and embargo. walk_forward() supports purge_bars and embargo_bars to prevent label overlap and autocorrelation leakage across train/test boundaries.
All of the above is verified by a public test suite of 178 tests. The honesty guarantees are executable: if the engine ever stopped charging costs, applying lag, or deflating for trials, a test would fail. Run pytest -q and read the assertions for yourself — the documentation and the code cannot drift apart.

This is the whole philosophy in one sentence: a backtest should be adversarial toward its author. AlphaForge takes that seriously so that when a strategy clears its bar, you can trust the result enough to risk capital on it.
